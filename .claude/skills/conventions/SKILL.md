## 2. The delivery loop

- **Branch:** `<type>/<short-topic>` in kebab-case: `feat/`, `fix/`, `chore/`, `refactor/`, `docs/`, `release/vX.Y.Z`. Commit messages and PR titles follow Conventional Commits ("rename to semver standard feat/fix/refactor, etc... for branch and commits"). Make a new branch as needed and commit consistently.
- **PR:** open it when the work is done, without being asked. Fill the repo's PR template. Retitle on request ("Rename the PR").
- **Merge:** when the user says "merge it" or the repo's CLAUDE.md says to auto-merge, merge once CI is green. Follow the repo's merge method (crate-arcade, loot-arcade and ICPSignal use squash). Resolve merge conflicts yourself ("Fix merge conflicts", "merge main in").
- **Delete the branch after merge.** In cloud sessions the git proxy answers HTTP 403 to remote branch deletion; say so once and point to the PR's delete button instead of retrying. Before deleting "stale" branches, check for unmerged commits.
- **Scope:** split big work into smaller PRs ("make individual branches that are smaller"), one PR per repo on cross-repo changes, unrelated fixes in their own PR, "Merge all open PRs except the release".
- **Releases:** release-please ("Cut the release with release please", "Start at V1.0.0"). Build and push images to GHCR only when a release is cut; deploy staging on every push to main.
- **Backlogs:** "Continue solving github issues and make PRs, and merge" is a normal hand-off. Work the issues in order, one PR each, until done.

## 3. Working style

- **Terse imperatives, no spec.** Decide and finish. Clarifying questions mostly go unanswered; make the reasonable call and state it. "Do it yourself", "Don't stop until finished", "Finish everything", "yes, open the PR and continue with T13.4".
- **"Try again"** (21 sessions) and a re-sent prompt mean the previous attempt did not land. Resume cleanly, do not restart from zero, and do not repeat steps already tried ("I already followed those instructions and it still isn't working").
- **Raw pasted logs or errors are the bug report.** Diagnose from the repo and the environment; fix or explain. Verify against the real environment when asked ("Use docker and my local terminal to check this").
- **Questions get answers first.** "Is X implemented properly?", "Why is the sources tab empty?" want findings, then wait for "go ahead" before changing code.
- **Discuss, then build everything.** Product and architecture work starts with "let's discuss", a PRD or `DESIGN.md`, and GitHub issues or epics with task IDs (T15.8). Then "Great, implement all of this", "I love the suggestions, do all of them". Documents are the source of truth; update them with the code. Document the how and the why.
- **Long voice-dictated prompts** happen; interpret for intent. Hard constraints come in capitals and mean it: "Use the exact sine wave formula... Do NOT modify it."
- **Narrow corrections.** "Only the api functionality for the removed buttons, not all the deposit logic", "leave the background alone but refit the machine". Keep scaffolding for planned features; remove abandoned work completely ("Undo all of this work").
- **Mine prior work.** "Scour the past chats", "Gather all insights from other chats and add them to the insights md file", "Use the GitHub repo TopstepX on my GitHub for the provider". Look in the user's repos and docs before building something new.
- **Cost-aware on infrastructure** ("I'm cheap right now", "keep costs as low as possible"), top models for hard work.

## 4. Engineering preferences

- **Config and secrets:** DB-backed settings editable in the admin panel or a frontend form; admin values override `.env`; keep `.env`, `app.env` and `deploy.env` in sync; prices and plan rules editable from the admin panel; "update the annual price when updating the monthly price".
- **Feature gating:** new behavior behind a feature flag or admin toggle; automations come with an opt-out; "Add this as an option, not the rule"; admin routes unreachable when disabled; UI elements conditional on sign-in.
- **Reach every surface:** a feature lands in backend, frontend, CLI and admin panel together; removal comes out of both ends; "Do this for all slot machines", "all social media services".
- **Parity across ports:** Rust, Go and Python implementations stay in parity ("Add this to the Rust, Go, and Python models"); sibling components get the same change (LatticeFSM when RadixCyclicNN changes).
- **Architecture:** interface-driven and dynamic so providers can be added later; "Modularity, clean code, and separated code"; APIs "LLM- and MCP-friendly"; expose products as MCP servers; additive changes keep the old implementation selectable; real implementations, not stubs; no artificial limits ("unlimited file size").
- **UX:** clear user-facing copy ("As a user, I don't know what fast grade is"), fewer buttons, tooltips and hover hints, forms over raw JSON, never show internals (design-doc references, model cost) to end users, show "behind the scenes" progress counts, HTML email templates.
- **Tests:** add them with the change ("Add tests for other formats of URLs"); never weaken assertions; engine tests with idempotency keys for games. Experimental ML code may skip tests when told.
- **Scraping and outreach:** "Never go full speed/max out the rate limit"; one IP and browser fingerprint per account, recorded in the DB; handle `X-Ratelimit-*` headers; warn users about ban risk; login-capable scraping behind a flag.
- **Trading (FinanceAI, FinTools):** "Less is more in trading. accuracy is better than volume"; focus on price, volume and volatility; backtests on real data (ES, daily 1m).

## 6. Known pitfalls

- Remote branch deletion from a cloud session returns 403 from the agent proxy.
- GHCR pushes need a token with `write:packages`.
- A `MAIL_FROM` on `example.com` makes Resend return 403.
- Tracked `__pycache__` files in ASI dirty the tree after tests; restore, do not commit.
- Cloud sessions have no TopstepX or exchange credentials unless added as environment secrets.
